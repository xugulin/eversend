"""远程（互联网）音视频通话：方案留档，暂未实现。

为什么先不做
------------
局域网的传输、聊天已经能用了；通话是另一个量级的东西，而且**这个项目的形态
决定了它必须走 WebRTC**：

* 手机端是浏览器页面。浏览器里唯一能拿到摄像头/麦克风并做实时音视频的通道就是
  ``getUserMedia`` + ``RTCPeerConnection``，没有第二个选择。
* 桌面端是 Python（PySide6）。要让桌面端加入同一通通话，就得在 Python 里实现
  ICE、DTLS-SRTP、拥塞控制（GCC/BBR）、抖动缓冲这一整套 —— 那比现在整个项目还大，
  而且质量注定不如现成的 WebRTC 栈。

所以诚实的路线是：**通话走 WebRTC，服务端只做信令**，而"服务端"就是我们已有的
HTTP 接口；媒体永远点对点，不经过任何中转（与文件传输的原则一致）。

分两步走
--------

**第一步（浏览器 ↔ 浏览器，局域网）**

双方都打开韧传网页版（手机、平板、另一台电脑的浏览器都行）时，可以通话：

1. 信令复用现有连接：``POST /api/call/offer`` / ``/api/call/answer`` /
   ``/api/call/candidate``，消息体就是 SDP 与 ICE candidate，落在一个
   ``calls`` 表里，对方用 SSE 或轮询取走（现有 ``/api/events`` 通道足够）。
2. ICE 只收集主机候选（局域网直连，不需要 STUN/TURN）；``iceServers: []``
   即可，避免任何外部依赖 —— 这一点和"纯局域网、不经过服务器"的定位一致。
3. 需要 **HTTPS**：``getUserMedia`` 只在安全上下文可用，而自签证书的 HTTPS 端口
   已经在 1.1 里做好了（``core/tls.py``）。
4. 页面里加一个通话浮层：``<video>`` 两个（本地小窗 + 远端全屏）、挂断按钮、
   静音/关摄像头开关。
5. 状态机：``ringing`` → ``accepted`` → ``connected`` → ``ended``，加超时（30 秒
   无人接听则取消）。信令消息要带 ``callId``，避免两通电话串线。

工作量估计：页面 ~400 行 JS，服务端 ~200 行（转发 + 状态），测试可以在 CI 里用
两个 headless Chrome 通过 CDP 建通话并断言 ``RTCPeerConnection.connectionState``
变成 ``connected``（模拟器有没有摄像头不影响 ICE 连通性验证）。

**第二步（电脑 ↔ 手机 / 电脑 ↔ 电脑，可选）**

要让**桌面原生窗口**参与通话，可选的路：

* 内嵌一个 WebView（QtWebEngine）来跑同一套 WebRTC 页面。代价：QtWebEngine 在
  PySide6-Essentials 里没有，要换成 Addons，绿色包体积 +100 MB 左右。
* 或者：桌面端只做"通话中转页面"（打开系统浏览器），原生窗口不参与。
  诚实但不优雅。

推荐第一步先做，第二步按实际需要再决定 —— 而且第一步做完，"手机和手机、
手机和电脑浏览器"这三种组合就已经能视频通话了。

不在计划内的
------------
* 不打算自己实现一套 RTP/RTCP：那不是这个项目的重点，而且注定做得更差。
* 不做通话录制、不做屏幕共享（screen share 是 WebRTC 的另一个 API，
  做起来不难，但属于"以后再说的功能"）。
