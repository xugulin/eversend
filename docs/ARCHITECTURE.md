# 架构说明

面向要读代码或改代码的人。协议细节在 [`PROTOCOL.md`](PROTOCOL.md)，
设计依据在 [`RESEARCH.md`](RESEARCH.md)。

## 1. 分层

```
┌──────────────────────────────────────────────────────────────┐
│  前端（三个，都只调用 Engine）                                  │
│  desktop/  PySide6 桌面    web/  手机浏览器    cli.py  命令行    │
└───────────────────────────┬──────────────────────────────────┘
                            │  Engine：devices / send / cancel / events
┌───────────────────────────▼──────────────────────────────────┐
│  core/engine.py     门面：身份、配置、服务器、会话注册、信任列表  │
└───────┬───────────────────────────────┬──────────────────────┘
        │                               │
┌───────▼─────────┐           ┌─────────▼──────────────────────┐
│ core/discovery  │           │ core/transfer                  │
│ 组播/广播/mDNS/  │           │  SendSession / ReceiveSession   │
│ 扫描/手动        │           │  拉取调度、恢复、修复            │
└───────┬─────────┘           └─────────┬──────────────────────┘
        │                               │
┌───────▼───────────────────────────────▼──────────────────────┐
│  core/connection.py   握手 + AEAD + 帧收发（唯一懂 crypto 的地方）│
│  core/framing.py      12 字节头 + 零拷贝 read_into / sendmsg    │
└───────┬───────────────────────────────┬──────────────────────┘
        │                               │
┌───────▼─────────┐           ┌─────────▼──────────────────────┐
│ core/sockutil   │           │ core/chunkstore                │
│ 网卡/socket 调优 │           │ .part + 追加日志 + 断点续传      │
└─────────────────┘           └────────────────────────────────┘
```

**核心原则：`core/` 不导入 PySide6，也不导入 `web/`。**
它只用标准库 + `cryptography`。这样同一个内核可以驱动桌面界面、浏览器界面、
命令行，将来也能配合 Chaquopy 打包成安卓原生 App。

## 3. 线程模型

EverSend **完全不用 asyncio**，用阻塞 socket + 线程。理由：

- 每个线程做的是"读一大块 → 算 CRC → 写盘 → 发下一块"这种**顺序、批量**的工作，
  协程带来的调度开销换不到任何东西。
- CPython 在阻塞 socket I/O 和大于 2047 字节的 `hashlib.update()` 上**会释放 GIL**，
  所以这些线程是真并行的。
- 阻塞代码里没有"忘了 await"这类 bug。

| 线程 | 数量 | 生命周期 |
|---|---|---|
| accept 循环 | 每监听 socket 一个 | 引擎运行期 |
| 对端连接处理 | 每入站连接一个 | 该连接 |
| 接收方控制读线程 | 每会话一个 | 该会话 |
| 接收方块工作线程 | 每数据流一个 | 该文件 |
| 接收方控制读线程 | 每会话一个 | 该会话 |
| 发送方流服务线程 | 每数据流一个 | 该会话 |
| 发送方 supervisor | 每会话一个 | 该会话 |
| 发现接收循环 | 每 discovery socket 一个 | 引擎运行期 |
| 公告循环 | 1 | 引擎运行期 |
| 摘要/报告短任务 | 临时 | 秒级 |

一个 4 流的传输大约 12 个线程。**线程之间只通过两种东西共享状态**：
带锁的小结构（位图、计数器、注册表）和线程安全的 `queue.Queue`。
没有共享的可变缓冲区。

> **踩过的坑**：`FileReader` 最初让同文件的所有流共用一个读缓冲，
> 结果两条流互相覆盖对方的数据——**静默的数据损坏**。
> 现在缓冲区是 `threading.local()` 的。这类 bug 是"单流测试永远发现不了"的。

## 4. 一次传输的数据流

```
文件 ──preadv──► 可复用缓冲 ──crc32──► sendmsg([帧头, 块头, memoryview])
                                              │
                                        内核 gather write
                                              │
   ┌──────────────────────────────────────────┘
   │
   ▼
接收缓冲 ──recv_into──► memoryview ──crc32──► os.pwrite(offset)
                            │
                            └──► IncrementalFileHasher.update(offset, view)
```

- **发送方零分配**：`os.preadv` 填进预分配的 `bytearray`，
  `sendmsg` 用 iovec 让内核 gather。对比 `os.pread` 每次分配一个 4 MiB 的
  `bytes` 对象——一个大文件就是几万次分配。
- **接收方零拷贝**：`recv_into` 直接读进可复用缓冲，`memoryview` 切片后
  直接 `os.pwrite`，全程没有 Python 层的 `memcpy`。
- **哈希重叠在传输里**：块按文件顺序发放，所以增量哈希器通常能连续折叠整个文件，
  **完全不需要传完再读一遍**。乱序时它会"停车"等待缺口；
  停车数据过多就放弃快速路径，改用一次顺序读。

## 5. 五条不变式

改代码时如果破坏了这几条，会出难查的 bug：

1. **块索引 → 偏移的映射由文件大小确定性地推出，从不由对端告知。**
   两端用同一个纯函数（`constants.pick_chunk_size`）。
   对端若声称一个不一致的偏移，接收方直接拒绝该块。

2. **先写数据，再追加日志记录。**
   反过来会让崩溃后的日志声称某些块存在而盘上是垃圾。
   这个顺序下崩溃只有一种结局：重下几块。

3. **成功必须有明确的报告。**
   "没有收到失败"不等于成功。未知一律按失败处理——
   误报失败只是重传一次（续传让它变成空操作），误报成功会丢数据。

4. **块级超时必须远小于流级超时。**
   被网络静默杀死的连接在阻塞的 reader 看来完全健康，
   唯一能结束等待的就是超时。用流级超时会把 2 秒的抖动变成 2 分钟的停摆。

5. **`core/` 不导入任何 UI 框架。**
   一旦破坏，浏览器界面和命令行就会莫名其妙地依赖 PySide6。

## 6. 恢复机制是怎么长出来的

三个机制不是一开始就设计好的，是被 `tests/test_resilience.py`
（一个会每 0.35 秒 RST 掉一条随机连接的代理）逼出来的：

| 观察到的现象 | 根因 | 现在的做法 |
|---|---|---|
| 控制连接一断就整个放弃 | 控制消息被绑在控制连接上 | 控制消息可以走**任意存活的数据流**；接收方按消息类型分派而不是按连接 |
| 所有连接同时死时接收方无法求援 | 求援请求本身没有通道可发 | 发送方有 **supervisor 线程**主动补流，不依赖接收方 |
| 恶劣网络 2.6 秒烧完 6 次重试 | 重试预算按**次数**算 | 改成**墙钟时间**（180 s）+ 次数上限（60） |
| 传输完成了但发送方报失败 | "send 没抛异常"当成送达了 | 完成报告在 3 秒窗口内**在所有通道上重复发送** |
| 明明传完了却卡 60 秒 | 摘要回复落在没人读的数据流上 | **谁发的请求谁读回复**（63.2 s → 2.0 s） |
| 偶尔报 `unknown transfer` | 补流连接撞上"接收方已忘记会话" | 保留一个"最近完成"窗口，竞态到达的连接安静关闭 |

## 7. 性能相关的取舍

| 决定 | 收益 | 代价 |
|---|---|---|
| 二进制分帧，不走 HTTP | 去掉 HTTP 头与 TLS 记录层 | 不能用现成的 HTTP 工具调试 |
| 块 1–16 MiB（而非 128 KiB） | 每字节固定开销降低 3 个数量级 | 内存占用与块大小成正比（已按流复用缓冲） |
| 接收方驱动（拉取） | 续传免费、负载自动均衡、发送方内存有界 | 多一次请求-回复交互（用流水线窗口摊掉） |
| 块按文件顺序发放 | 顺序写盘（HDD 上差 6 倍）+ 增量哈希 | 掉队块会短暂阻塞哈希器的快速路径 |
| 每网卡一个组播 socket | 多网卡机器也能被发现 | socket 数量随网卡数增长 |
| 线程而非协程 | 无"忘了 await"、大缓冲 I/O 真并行 | 每传输约 12 个线程 |

**socket 缓冲要在 connect 之前设置。** Linux 在内核里把自动调优的上限冻结在
连接建立的那一刻，之后再 `setsockopt` 只能改已分配的部分。
所以 `tune_socket()` 必须在 `connect()` 前调用——这是"单流吞吐莫名卡在 100 Mbps"
的经典原因。

## 8. 界面层

### 8.1 桌面（PySide6）

- `bridge.py` 把引擎事件转成 Qt 信号。引擎在普通线程上跑，
  信号接收者在 GUI 线程上，Qt 自动用队列连接跨线程投递——
  **槽函数永远在 GUI 线程执行**，可以安全操作控件。
- `EngineBridge._on_event` 把整个分派包在 `try/except` 里：
  一个界面信号绝不能弄死一条传输线程。
- `send()` 会阻塞，所以放在 `SendWorker` 线程里，完成时发一个 Qt 信号回来。

### 8.2 浏览器（手机）

- 纯标准库 `ThreadingHTTPServer`。理由同第 3 节：不用为此引入 aiohttp。
- 事件用 **SSE** 推给页面；同时前端每 3 秒轮询 `/api/state` 兜底
  （某些代理会缓冲 SSE）。
- 上传走 `XMLHttpRequest`（不是 `fetch`），因为只有它给真实的 `upload.onprogress`。
- **安全**：每次启动生成 CSRF 令牌并要求放在请求头；校验 `Host` 头防 DNS rebinding；
  路径解析后复核仍在允许目录内；请求体有上限。
- **谁连上了**：每个通过校验的请求都按来源 IP 记一次"这个浏览器还在"
  （`WebUI.touch_client`，15 秒 TTL），`/api/state` 的 `webClients` 把它交出去。
  桌面端读同一份数据，在「设置 → 已连接的手机」和扫码弹窗里显示
  「✅ 已连接：192.168.1.23（Android 上的 Chrome）」。

  为什么必须有这一条：手机是**浏览器客户端**，永远不会出现在左侧的设备列表里
  （那是协议层的对端列表）。在加它之前，扫码之后整个桌面端没有任何变化，
  用户唯一能得出的结论就是"没连上"。**一个功能"在工作"和"看得出来在工作"
  是两件事**，后者得专门做。

### 8.3 手机为什么是浏览器而不是 App

PySide6 官方**不支持 Android**（只有 Linux/Windows/macOS 的 wheel）。
要做到"零安装"，浏览器是唯一路径。内核是纯标准库的，
将来要用 Chaquopy 做成原生 App，需要写的只有 Android 那一层。

## 9. 便携性是怎么保证的

- 所有路径从**启动器自己的位置**推导（`$0` / `%~dp0`），绝不依赖 `$PWD`。
- `desktop/app.py` 的 `portable_root()` 读 `EVERSEND_HOME`（启动器设置），
  源码运行时回退到当前目录。
- `writable_dir()` 探测目标目录能否真写（写一个探针文件再删）；
  只读介质（写保护的 U 盘、锁定的 SD 卡）自动退到系统临时目录，**并告知用户**。
- 不写注册表、不写 `%APPDATA%`、不写 `~/.config`。所有状态在 `data/` 下。
- 打包时把 `.py` 编译成 `.pyc` 以减少体积和启动时间，
  但**保留 `app/` 的源码**——用户应该能看见并修改他拿到的东西。

## 10. 想改代码的话

**加一个新的前端**：读 `Engine` 的公开方法就够了
（`devices` / `send` / `cancel` / `resolve_offer` / `active_transfers` /
`pending_offers` / `self_peer` / `events.subscribe`）。
不要碰 `core/`。

**加一个新的发现方式**：在 `DiscoveryService` 里加一对收发循环，
把结果喂给 `PeerStore.upsert` 即可。所有通道共用同一张设备表，
按 `device_id` 去重。

**改协议**：先改 `constants.py`（唯一事实来源），再改 `PROTOCOL.md`，
最后才是 `transfer.py`。`PROTOCOL_VERSION` 要跟着动。

**改块大小**：改 `constants.py` 里的 `TARGET_CHUNKS_PER_FILE` / `MIN` / `MAX`。
因为两端用同一个纯函数推导，所以不需要协商——但**旧版本客户端会算错偏移并拒绝块**，
属于不兼容变更。

**跑测试**：见 README 的"测试"一节。改动 `transfer.py` 后
**必须**跑 `test_resilience.py`——协议层面的回归在完美回环上测不出来。
