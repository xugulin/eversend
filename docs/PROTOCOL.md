# EverSend 线协议规范 v1

本文是 `src/eversend/core` 实现的**权威描述**。所有整数都是**网络字节序（大端）**，除非另有说明。

---

## 1. 传输与端口

| 端口 | 协议 | 用途 |
|---|---|---|
| 52117 | TCP | 控制连接 + 数据流（同一个监听端口） |
| 52118 | UDP | 组播 / 广播发现 |
| 52119 | TCP | 浏览器（手机）界面，可选 |
| 5353 | UDP | mDNS（与系统共享） |

一条传输由 **1 条控制连接 + N 条数据流**组成，全部连到同一个监听端口。每条连接都独立完成下面第 2 节的握手。

---

## 2. 帧格式

```
偏移  长度  字段
0     4     magic = "EVSD"
4     1     type
5     1     flags
6     2     stream          （保留，恒 0；见下方说明）
8     4     length          （payload 字节数）
12    N     payload
```

头部固定 12 字节（`FRAME_HEADER = "!4sBBHI"`）。

**flags**

| 位 | 含义 |
|---|---|
| 0x01 | payload 已被 AEAD 封装 |
| 0x02 | 保留（压缩，未使用） |
| 0x04 | 保留（分片末帧，未使用） |

**上限**：单帧 payload ≤ 64 MiB（`MAX_FRAME_PAYLOAD`）。超出即视为协议违规并断开——这是防止恶意/损坏对端让接收方无限分配内存的硬闸。

> **为什么 `stream` 字段不参与加密的 AAD**：流之间已经由"不同的 TCP 连接"隔离，而这个字段由发起方分配、接收方要更晚才知道。把它绑进 AAD 会让连接建立后的一段时间内所有帧都解不开，而且没有任何安全收益。AAD 只绑定 `type`。

## 3. 握手（2 个往返，双向认证）

### 3.1 流程

```
发起方 I                                        响应方 R
   |-- HELLO ────────────────────────────────────>|   {proto, device, x25519, ed25519, nonce_i, encrypt}
   |                                              |
   |<─────────────────────────────── HELLO_ACK ---|   {proto, device, x25519, ed25519, nonce_r, encrypt, sig_r}
   |                                              |
   |   [双方在此推导会话密钥]                        |
   |                                              |
   |-- AUTH ─────────────────────────────────────>|   {sig_i}        （已加密）
   |<────────────────────────────── AUTH_OK ──────|   {ok, authenticated}
```

- `HELLO` 和 `HELLO_ACK` 是**明文**（它们承载密钥材料）。
- `AUTH` 与 `AUTH_OK` 在会话建立之后发送，因此**已加密**。
- 响应方在发出 `HELLO_ACK` **之前**就已安装会话，所以 `AUTH` 一定能被解开。

### 3.2 密钥推导

```
shared       = X25519(own_secret, peer_public)
salt         = SHA-256(nonce_i || nonce_r)
session_key  = HKDF-SHA256(ikm=shared, salt=salt, info="eversend/v1/session", len=32)
```

`salt` 里同时含双方 nonce ⇒ **重放同一次握手必然得到不同的密钥**。

### 3.3 签名与转录

双方签名的字节串完全相同：

```
transcript = "eversend/v1/handshake" | id_I | id_R | x25519_I | x25519_R | nonce_i | nonce_r
```

用各自的 Ed25519 长期私钥签名（`crypto.handshake_transcript`）。

- `sig_r` 让发起方确信响应方身份；
- `sig_i` 让响应方确信发起方身份。

把每一个握手元素都绑进转录，是为了让中间人无法"借用"别人的握手参数重放。

### 3.4 短认证串（SAS）

```
sas = SHA-256("eversend/v1/sas" || session_key)[:4] mod 10^6   → 6 位十进制
```

两端显示同一个 6 位数。能转发流量但伪造不了签名的中间人**必然让两边数字不一致**，一眼可辨。这比让用户敲 PIN 更不容易出错。

### 3.5 无加密降级

`cryptography` 不可用时，会话退化为 `NullCipher`：AAD/签名全部跳过，`authenticated=False`，**UI 必须显著提示**。绝不静默降级。

## 4. AEAD 与 nonce

| 项 | 值 |
|---|---|
| 算法 | AES-256-GCM（x86-64 / ARM64，有 AES 加速）或 ChaCha20-Poly1305 |
| nonce | 12 字节 = 4 字节方向前缀 + 8 字节大端计数器 |
| 方向前缀 | 发起方加密用 `00 00 00 01`，响应方用 `00 00 00 02` |
| 计数器 | 每条连接、每个方向独立，从 0 自增，**不上线** |
| AAD | `type` 单字节 |
| tag | 16 字节 |

方向前缀不同 ⇒ 两个方向**永不共用 nonce**。计数器在可靠有序的 TCP 上不会错位。

**块帧的 AAD 是 `type || chunk_header`**：这样攻击者无法把一块数据搬到别的偏移上（见 5.2）。

## 5. 消息

### 5.1 控制消息（payload 是 UTF-8 JSON）

| 值 | 名称 | 方向 | 载荷 |
|---|---|---|---|
| 0x01 | HELLO | I→R | `proto, device, x25519, ed25519, nonce, encrypt` |
| 0x02 | HELLO_ACK | R→I | 同上 + `sig` |
| 0x03 | AUTH | I→R | `sig` |
| 0x04 | AUTH_OK | R→I | `ok, authenticated` |
| 0x05 | ATTACH | I→R | `t`(transfer id), `i`(流序号), `sender`(设备 id) |
| 0x06 | NEED_STREAMS | R→I | `t, n` —— 请求补充数据流 |
| 0x10 | OFFER | I→R | `transferId, files[], totalBytes, streams, pin, sender` |
| 0x11 | OFFER_ACK | R→I | `transferId, accepted[], rejected[], streams, resumeBytes, totalBytes, saveDir` |
| 0x12 | OFFER_REJECT | R→I | `transferId, reason` |
| 0x20 | CHUNK_REQ | R→I | `t, f`(文件序号), `i`(块序号) |
| 0x21 | CHUNK | I→R | **二进制**，见 5.2 |
| 0x30 | FILE_DONE | R→I | `t, i, ok, path` |
| 0x33 | DIGEST_REQ | R→I | `t, i` —— 索要整文件摘要 |
| 0x34 | FILE_DIGEST | I→R | `t, i, h`(blake2b-256 十六进制) |
| 0x32 | TRANSFER_DONE | R→I | `t, status, bytes, files, error` |
| 0x38 | PROGRESS | R→I | `t, bytes, total, files` |
| 0x40 | CANCEL | 双向 | `t, reason` |
| 0x41 | ERROR | 双向 | `message` |
| 0x50/0x51 | PING/PONG | 双向 | 不透明字节，原样回送 |
| 0x60 | BYE | 双向 | 空 |

> **控制消息不绑定连接。** 接收方按 `type` 分派，而不是按"它从哪条连接来"。这正是控制连接断掉后传输还能继续的原因（见第 8 节）。

### 5.2 CHUNK 帧（热路径）

`type = 0x21`，payload 布局：

```
0   4   seq        文件序号（= OFFER 里 files[].i）
4   4   index      块序号
8   8   offset     字节偏移 = index × chunk_size
16  4   length     本块数据字节数
20  4   crc32      数据的 CRC32（zlib 多项式）
24  N   data       块数据（加密时是密文||16 字节 tag）
```

块子头 **24 字节保持明文**并作为 AAD 的一部分被认证：攻击者能看见但改不了。

开销：24 + 12（帧头）= 36 字节 / 块。1 MiB 块 → **0.0034%**。

**零拷贝**：
- 非加密时，`sendmsg([帧头, 块头, memoryview(文件缓冲)])` 由内核 gather，Python 层零拷贝；
- 接收时 `recv_into` 直接读进可复用的块缓冲，再 `os.pwrite` 落盘，全程零拷贝。

## 6. 分块策略

```python
chunk_size = clamp(align64k(file_size // 4096), 1 MiB, 16 MiB)
```

即"目标每个文件约 4096 块"。两边用**同一个纯函数**算，无需协商：

| 文件大小 | 块大小 | 块数 |
|---|---|---|
| 4 MiB | 1 MiB | 4 |
| 512 MiB | 1 MiB | 512 |
| 64 GiB | 16 MiB | 4096 |

4096 块 ⇒ 位图 512 字节，逐块记账的开销可以忽略。

**块数与块大小必须在两端完全一致**——`index → offset` 的映射依赖它。因为它由文件大小确定性地推出，所以从不由对端"告知"，而是各自计算。

## 7. 传输时序

```
接收方 R                                                发送方 I
   |<────────────────────────── OFFER ────────────────────|   （控制连接）
   |                                                       |
   |  decide()：解析续传状态、建 .part 文件、决定接受哪些      |
   |-- OFFER_ACK ─────────────────────────────────────────>|   accepted[] / streams / resumeBytes
   |                                                       |
   |                                          [I 并发打开 N 条数据连接]
   |<── ATTACH ×N ─────────────────────────────────────────|
   |                                                       |
   |  对每个文件（按大小降序）：                              |
   |    把缺失块放进共享队列                                |
   |    每条流：取一个块 → CHUNK_REQ → 收 CHUNK → 校验 → pwrite → 记账
   |-- CHUNK_REQ ─────────────────────────────────────────>|
   |<────────────────────────────── CHUNK ─────────────────|
   |                                                       |
   |-- DIGEST_REQ ────────────────────────────────────────>|
   |<───────────────────────────── FILE_DIGEST ────────────|
   |  校验整文件哈希；不匹配则只重取坏块                       |
   |-- FILE_DONE ─────────────────────────────────────────>|
   |                                                       |
   |-- TRANSFER_DONE ─────────────────────────────────────>|   （在所有存活通道上重复 3 秒）
```

### 7.1 为什么是拉取（接收方驱动）

- 续传免费：接收方只是"不请求已有的块"。
- 负载自动均衡：流从共享队列取任务，快的自然拿得多。
- 发送方内存有界：无论多少条流，手里只有一个块。

### 7.2 为什么要流水线

每条流维持 `window = clamp(DEFAULT_WINDOW_BYTES / chunk_size, 2, 8)` 个在飞请求。若每块都"发请求→等回复"，则每块之后都有半个 RTT 的空闲；LAN 上无所谓，100 ms RTT 的广域网上会把吞吐锁死在 `chunk_size / RTT`。TCP 有序，所以回复按请求顺序到达，用一个 FIFO 就能配对。

### 7.3 为什么按文件顺序发放块

共享队列按升序发块 ⇒ 多条流合起来是从前往后顺序写盘。在机械硬盘上这是数量级的差别。附带好处：整文件哈希可以边收边算（`IncrementalFileHasher` 折叠连续前缀），正常情况下**完全不需要传完再读一遍**。

## 8. 中断、续传与恢复

### 8.1 落盘布局

```
<目标文件>.eversend.part      预分配到完整大小，块用 pwrite 写在最终偏移
<目标文件>.eversend.journal   追加式日志
```

日志格式：

```
magic "SWDJ"(4) | version(1) | flags(1) | reserved(2) | header_len(4) | header(JSON) | records...
record = (u32 chunk_index, u32 crc32)     每条 8 字节
```

**写入顺序是被刻意安排的：先写数据，再追加日志记录。** 于是一次崩溃只有一种可能结局——"日志里有、盘上没有"（多下几块），永远不会是"盘上有、日志说没有"（静默丢数据）。

### 8.2 恢复

重启后重放日志重建位图；撕裂的尾记录被忽略（那只意味着崩在"写完数据、还没追加日志"之间，重下即可）。日志头里的 `(size, chunkSize, mtime)` 必须完全匹配才允许续传——所以同名同大小但已修改的文件不会被错误续上。

### 8.3 校验失败 → 修块，不重传

整文件摘要不匹配时，用日志里记录的**逐块 CRC** 扫出到底哪几块坏了，只重取那几块。100 GB 的传输坏一个扇区，代价是 4 MB，不是 100 GB。

### 8.4 连接全灭怎么办

这是最容易被忽略、也最难测的场景（一次 Wi-Fi 漫游会同时杀掉控制连接和所有数据流）：

1. **接收方**发现连接池空了 → 发 `NEED_STREAMS`；如果没有通道可发（控制连接也死了），就等发送方自己重连。
2. **发送方**有一个 supervisor 线程，每秒检查连接池大小，低于目标值就自己补——**不依赖接收方的请求**，因为请求本身可能根本发不出来。
3. 断掉的流手里在飞的块全部回到共享队列，被存活的流接走。
4. 全文件重试预算是**墙钟时间**（180 s）而不是次数上限。把"连接被反复掐断"和"这几块一直失败"混为一谈是错的：恶劣网络两秒钟就能烧掉六次重试。
5. 完成报告在 3 秒窗口内**在所有存活通道上重复发送**。因为"本地 send 没抛异常"不能证明送达——被网络杀死的连接照样接受写入，RST 之后才回来。

### 8.5 超时

| 名称 | 值 | 用途 |
|---|---|---|
| `CHUNK_REQUEST_TIMEOUT` | 8 s（下限） | 一个已请求的块多久没回来就换流 |
| 同上，按块大小放大 | `max(8s, chunk_size / 512 KB/s)` | 16 MiB 块 → 32 s |
| `STREAM_IDLE_TIMEOUT` | 30 s | 整条流的存活底线 |
| `CONTROL_LOSS_GRACE` | 120 s | 控制连接丢失后等报告的上限 |
| `FILE_RECOVERY_BUDGET` | 180 s | 单个文件的恢复总预算 |
| `HANDSHAKE_TIMEOUT` | 10 s | 握手 |
| `OFFER_TIMEOUT` | 300 s | 等用户点"接受" |

**块级超时必须远小于流级超时**：被静默杀死的连接在阻塞的 reader 看来完全健康，唯一能结束等待的就是超时；用流级超时会让一次两秒的抖动变成两分钟的停摆。

## 9. 发现

### 9.1 公告（UDP，单向下发）

```json
{"t":"eversend/1","id":"<device_id>","n":"名称","k":"desktop","p":"linux",
 "v":"1.0.0","port":52117,"web":52119,"ts":1789998139}
```

- 组播 `239.255.83.68:52118`（管理域范围，路由器不转发），**刻意避开 LocalSend 的 224.0.0.167**，两个应用可以在同一局域网共存而不互相刷屏。
- 同时发广播：`255.255.255.255` 与每个网卡的有向广播地址。**IGMP snooping 剪枝是"设备永远不出现"的头号原因**，广播常常还能到。
- **UDP 只用来喊，从不用来答。** 收到公告的一方若想通信，主动开 TCP。这让发现完全无状态：丢一个包只意味着晚一点知道。
- 公告连发 4 次（0 / 0.25 / 1.0 / 2.5 s），运行中每 30 s 重播。90 s 没消息视为离线。
- 自己的公告会回环收到，按 `device_id` 过滤。

### 9.2 为什么要一网卡一 socket

一个组播 socket 只能从它最后一次 `IP_MULTICAST_IF` 指定的网卡发包。要覆盖多网卡就必须每块网卡一个 socket，配 `SO_REUSEADDR` + `SO_REUSEPORT`（多个实例、或重启撞上旧进程时也能绑上）。

### 9.3 mDNS

额外加入 `224.0.0.251`，把服务注册为 `_eversend._tcp.local`（PTR/SRV/TXT/A）。理由很实际：**不少消费级 AP 会可靠转发 mDNS，却丢掉自定义组播组**。TXT 里放身份字段，端口从 SRV 记录取。

### 9.4 兜底

- **主动子网扫描**：对每个本地 /24 逐个 TCP 连接，并发 64。慢，但在"所有广播都被过滤"的企业/酒店网络上是唯一可行的手段。
- **手动 IP / 二维码**：客户端隔离、VPN 专线等场景的最后一招。

## 10. 安全边界（明确说明）

**能防住的**
- 伪造设备身份（需要 Ed25519 私钥）。
- 窃听或篡改载荷（AEAD，AAD 绑定帧类型与块偏移）。
- 握手重放（nonce 绑定密钥）。
- 路径穿越（`safe_join` 拒绝 `..`、绝对路径、盘符、NUL，并校验结果仍在目标目录内）。
- 恶意对端撑爆内存（帧上限、控制载荷上限、握手并发上限）。
- 浏览器端 CSRF 与 DNS rebinding（每次启动生成的令牌 + Host 头校验）。

**防不住的 / 信任假设**
- 同一局域网内的**流量分析**：帧类型、块索引、文件大小是可见的（密文长度也可见）。不隐藏元数据。
- 用户主动信任了一台恶意设备之后的后果。
- 未经认证的中间人可以做**透明转发**——此时两端的 SAS 数字会不一致，但需要用户真的去看。

**传输加密是可选的、且默认开启。** 关闭后仅剩 CRC32 完整性（能发现随机损坏，不能防篡改），UI 会明确告警。
