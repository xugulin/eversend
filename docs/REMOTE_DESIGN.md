# EverSend 远程（互联网）传输设计

> **状态**：设计完成，接口已预留（`src/eversend/remote/`），尚未接入界面。
> 局域网部分已完整实现并实测。本文是把 RustDesk 的穿透原理"学会之后重新设计一遍"的产物——
> 复用的是思想，不是代码，并且明确修掉它的三个已知缺陷。

---

## 1. 目标与非目标

**目标**
- 两端都在 NAT 后面时也能互传文件，不需要用户做端口映射。
- 优先直连（打洞），打洞失败才走中继，并且**在界面上说清楚当前是哪种**。
- 复用现有的整个传输内核——分片、续传、坏块修复、多流并行**一行都不用改**。
- 会合通道本身也必须加密，**不允许静默降级**。

**非目标**
- 不追求"任意 NAT 组合都能直连"。对称 NAT + 严格防火墙就是打不通，诚实回退到中继。
- 不做 WebRTC。见第 7 节。

---

## 2. 为什么现有内核不用改

这是整个设计里最关键的一点。

`Engine` 从上层看只有一个动作：**给我一个 `Peer`（有个地址和端口），我把文件送过去**。
它拿到 `Peer` 之后做的第一件事就是 `connect_to(peer.address, peer.port)`。

所以远程传输**不需要碰传输层**。它要做的事情只有一件：**在本地变出一个能连通的端点**。

```
                 ┌─────────────────────────────────────────┐
   Engine ──────►│  connect_to("127.0.0.1", 临时端口)        │
                 └──────────────┬──────────────────────────┘
                                │  本地回环（快、永不失败）
                 ┌──────────────▼──────────────────────────┐
                 │  Tunnel：一条到对端的真实数据通道          │
                 │  ├─ 直连（打洞成功）                       │
                 │  ├─ 中继（打洞失败）                       │
                 │  └─ IPv6 直连                             │
                 └──────────────┬──────────────────────────┘
                                │
                         公网 / NAT / 中继服务器
```

隧道对内核完全透明。于是**分片、续传、多流并行、坏块修复、加密握手全部原样生效**——
包括"多流"：每一条数据流可以在隧道里复用同一条底层连接（多路复用），
也可以各自打一条洞（更快但要更多端口）。

这也是 RustDesk 的做法：`KcpStream` 被包成 `Stream::Tcp(FramedStream(BytesCodec))`，
上层协议无感知。**这个抽象是正确的，值得照抄。**

## 3. 三个角色

### 3.1 会合服务器（Rendezvous）

**唯一职责：告诉每一端"我观测到的对方的公网地址"。**

- 客户端注册：`{device_id, public_key, 观测到的地址}`，每 15 秒心跳，30 秒判离线。
- 查询：A 想连 B → 服务器把 B 的观测地址给 A，同时把 A 的观测地址推给 B。
- **服务器永远只报告自己观测到的地址，绝不接受客户端自报 IP**（RustDesk 的核心经验）。
- 服务器**不是信任根**：它只做介绍人，看不到任何明文（见第 5 节）。

**信令一律走 TCP。** RustDesk 的开源服务器会显式丢弃 UDP 上的打洞信令
（`PunchHoleRequest` / `PunchHoleSent` / `LocalAddr` 在 UDP 分支里被忽略），
导致客户端代码里写好的 UDP 路径在自建部署下根本走不通。
既然是可靠信令，就老老实实走可靠通道，UDP 只用来做数据面探针。

### 3.2 中继服务器（Relay）

- 配对键是一个一次性 uuid；先到的一方等最多 30 秒，第二个同 uuid 到达即配对。
- 配对后**双向盲转发裸字节**：不解密、不解析、不注入控制帧。
- 定位清楚：**稳定但慢的兜底**。必须限速并单独计量，因为它的带宽成本是传输量的 2 倍。
- 无数据 30 秒断开。

### 3.3 客户端

负责：注册、维持心跳、发起打洞、多路竞速、失败回退中继、把隧道接到本地端点。

## 4. 打洞：学 RustDesk，但修掉它的坑

### 4.1 观测模型（照抄）

```
A（发起方）                 会合服务器                     B（被叫方）
   |── RegisterPeer（15s 心跳）──►│◄── RegisterPeer ──────────|
   |                              |                          |
   |── PunchHoleRequest{id:B} ───►|                          |
   |   （这条 TCP **挂住不关**）    |── PunchHole{A的观测地址} ─►|
   |                              |                          |
   |◄── PunchHoleResponse{B的观测地址} ── PunchHoleSent ──────|
   |                                                         |
   |◄════════ 双方同时向对方观测地址发起连接 ═════════════════►|
```

**必须挂住那条 TCP 连接**：`PunchHoleResponse` 要从它回程。RustDesk 的服务器把控制端那条
连接存进 `tcp_punch[源地址]` 就是干这个的。这是自己实现打洞时最容易踩的第一个坑。

### 4.2 TCP 打洞的关键细节（照抄）

1. **用"到会合服务器那条 TCP 连接的 `local_addr`"作为本地绑定地址。**
   这是"本机访问外网那块网卡的私网 IP + 临时端口"，比枚举网卡可靠得多，
   天然排除 Docker / VPN / 虚拟网卡。
2. **双方用同一个本地端口既 connect 又 accept。** NAT 映射才能对上。
   需要 `SO_REUSEADDR` + `SO_REUSEPORT`。
3. **一边反复 connect 一边 accept。** 打洞节奏 150 ms 起每次 ×1.5、封顶 2 s。
4. **截止后给在飞的 connect 留 3 秒尾巴。** 中途掐断会毁掉对端已经建立的连接——
   RustDesk 专门有个 `PUNCH_GRACE = 3000 ms` 就是为这个。
5. **accept 不过滤来源地址。** NAT 可能换外部地址池。

### 4.3 先判 NAT 类型，对称就直接中继（照抄）

用**同一个本地地址**分别连服务器的两个相邻端口，比较服务器观测到的源端口：
- 相同 → 锥形 NAT（打洞有戏）
- 不同 → **对称 NAT**（每个目的地一个外部端口，服务器告诉对端的端口必然无效）

RustDesk 的经验是：**只要有一端是对称 NAT，直接走中继，不要浪费 18 秒**。

### 4.4 同内网的本地地址交换（照抄）

如果两端其实在同一内网（公网 IP 相同，或都在服务器的局域网内），服务器让被叫端
**新建一条到服务器的 TCP 连接**，取它的 `local_addr` 回给发起方当候选地址。
这比枚举网卡准确得多，也天然过滤掉虚拟网卡。

> **EverSend 的局域网发现用的正是同一个思想**：与其猜哪块网卡对，
> 不如枚举真实接口、每个接口都发一遍公告，让对端用"收到包的那个接口地址"回连。

### 4.5 多路竞速（照抄，但简化）

RustDesk 同时跑 TCP / UDP-KCP / IPv6 / WebRTC 四条腿。EverSend 只跑两条：

1. **TCP 打洞** —— 成功率高，与中继同构，失败时的代码路径也最短。
2. **中继** —— 兜底。

再加一条**成本极低的可选腿**：**IPv6 直连**。两端都有公网 IPv6 时直接连，
根本不需要打洞（现代移动网络 IPv6 覆盖率已经很高）。

竞速策略：直连先赢就用；中继结果**压后 2.5 秒**再采纳，给直连留最后机会。

## 5. 加密：这正是 RustDesk 做错的地方

RustDesk 的端到端加密（客户端↔客户端）是**对的**：

```
被叫端 → SignedId{ sign(IdPk{id, 一次性 X25519 pk}, 长期 Ed25519 sk) }
发起端 → 用"服务器签名过的对端公钥"验签，并要求 id 匹配
       → 回 PublicKey{自己的临时 X25519 pk, 用 X25519 box 封的会话密钥}
```

但它的**会合通道**有严重问题（自建部署下）：

- 开源 hbbs **完全没有实现 `KeyExchange`**（服务端零命中）。
- 客户端只在带 `token` / `switch_code`（Pro 特性）时才尝试 `secure_tcp`。
- 于是 **自建部署下会合信令是明文的**。
- `PunchHoleResponse.pk`（服务器签名的对端公钥）**不可伪造，但可以被剥离**——
  剥掉之后客户端就降级到非加密会话，而且**界面上看不出来**。

**EverSend 的对策**：

1. **会合通道强制握手，不允许降级。** 复用现有的 `Connection` 类——
   它已经有双向认证握手、会话密钥绑定双方 nonce、SAS 短认证串。
   会合连接直接用它，服务器持有自己的 Ed25519 身份。
2. **"对端公钥存在"是硬要求。** 拿不到就无法建立会话，而不是安静地继续。
3. **降级必须可见。** 任何非加密状态都要在界面上明确标出，
   而不是靠用户自己去猜（RustDesk 有 `is_secured()`，但默认路径下它是 false 而用户不知道）。
4. **端到端加密与信令加密分离。** 文件数据的密钥由两端直接协商，中继和会合服务器都看不到。
   这一点 RustDesk 是对的，照抄。

## 6. 隧道与多路复用

一条隧道承载现有的"1 控制 + N 数据流"。

**方案 A（先做）**：隧道里做轻量多路复用。每个逻辑流一个 4 字节 stream id，
复用一个 TCP 连接。实现简单，NAT 上只占一个端口。

**方案 B（更快）**：每条数据流各自打一条洞，物理上真的并行。
RustDesk 的做法更接近这个（每条流一个 socket），吞吐更好但要占 N 个 NAT 映射。

建议：**默认 A，把 B 作为"追求极限速度"的选项**。
因为 EverSend 的多流本来是为了吃满带宽-时延积，而在广域网上，
一条 TCP 连接的窗口往往就够（瓶颈是链路带宽而不是窗口），多路复用的收益有限。

**隧道必须复用现有的分帧格式**，只是把"一个 TCP 连接"换成"隧道里的一条逻辑流"。
于是第 8 节的恢复逻辑（补流、块重取、报告重发）**原样生效**——
这正是不改内核的价值所在。

## 7. 为什么不用 WebRTC

LocalSend 的远程传输走 WebRTC 数据通道。EverSend 不这么做的理由：

1. **16 KiB 分片。** LocalSend 的数据通道分片是 16 KiB（`CHUNK_SIZE = 16 * 1024`），
   还要靠轮询 `buffered_amount()` 做背压。相比之下我们一块 1–16 MiB，
   靠 TCP 自身的流控。分片越小，每字节的固定开销越大。
2. **一整套 SDP / ICE / DTLS 依赖。** 而我们的绿色包只打算带两个 wheel
   （PySide6 + cryptography）。引入 WebRTC 意味着要么加一个重量级依赖，要么自己实现，
   两者都不划算。
3. **收益重叠。** WebRTC 最大的价值是"穿透 + 加密 + 拥塞控制"，而这三件事
   我们已经有（TCP 打洞、X25519/AEAD、TCP 拥塞控制）。
4. **它并不保证直连。** ICE 选中 TURN 中继时和我们的中继是一回事，
   但多了一层我们控制不了的复杂度。

如果将来要支持浏览器作为对端，WebRTC 才重新变得必要——那时它可以作为**第三条腿**
加进第 4.5 节的竞速，而不是替换掉整条路径。

## 8. 与传输内核的接口

```python
# src/eversend/remote/__init__.py（已存在）

class TransportKind:
    LAN      = "lan"       # 局域网直连
    DIRECT   = "direct"    # 公网直连（含 IPv6）
    PUNCHED  = "punched"   # 打洞成功
    RELAYED  = "relayed"   # 中继

class Transport:
    kind = TransportKind.LAN
    def connect(self, peer_id: str, timeout: float = 10.0): ...
    def close(self) -> None: ...
```

接入方式：远程传输启动时在本地起一个回环监听（`127.0.0.1:0`），
把隧道另一端接上去，然后给 `Engine` 一个指向它的 `Peer`。
**`Engine` 一行都不用改。**

需要新增的只有：
- `remote/rendezvous.py` —— 注册、心跳、查询、观测地址交换
- `remote/punch.py` —— NAT 类型自测、TCP 打洞、IPv6 直连
- `remote/relay.py` —— 中继协议客户端
- `remote/tunnel.py` —— 多路复用与本地端点
- `server/` —— 独立的会合 + 中继服务端（纯 Python，一条命令起）

## 9. 分阶段落地

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| 1 | 会合服务器 + 注册/心跳/查询 | 两台机器互相看得见对方的观测地址 |
| 2 | NAT 类型自测 | 能正确区分锥形/对称 |
| 3 | TCP 打洞 | 家用宽带（锥形）下直连成功率 > 80% |
| 4 | 隧道 + 多路复用 | 打洞成功后能传完一个 1 GB 文件 |
| 5 | 中继 | 对称 NAT 下也能传完，界面标注"中继" |
| 6 | 断线重连 | 拔网线 30 秒再插上，传输从断点继续 |
| 7 | IPv6 直连 | 双栈环境下跳过打洞直接连 |

阶段 6 几乎不用写新代码——内核的恢复逻辑已经做完了，这正是第 2 节那个抽象的价值。

## 10. 安全清单（上线前必须全部满足）

- [ ] 会合连接强制双向认证握手，**无降级路径**
- [ ] "对端公钥缺失"是硬错误，不是警告
- [ ] 文件数据的密钥由两端直接协商，服务器与中继都无法解密
- [ ] 界面明确显示当前路径：直连 / 打洞 / 中继，以及是否加密
- [ ] 会合服务器无法通过伪造地址把两端引到第三方（地址由服务器观测，但会话密钥由两端协商，中间人无法解密）
- [ ] 中继有限速与计量，防止被当作免费代理
- [ ] 注册接口有频率限制，防止 ID 抢注与枚举
- [ ] 中继的配对 uuid 一次性且不可预测
- [ ] 所有用户可见字符串都提示了"中继模式下服务器能看到流量元数据（大小/时序）"
